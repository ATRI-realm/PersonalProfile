## 1. 目标与范围

**目标**：生成供小学生练习的四则运算题。题目本身必须自洽——数值不越界、无负数、除法能除尽。
默认**只输出题面**；答案要不要带出来是一个渲染开关（命令行 `--show-answer`，网页版顶栏开关，见 §6.3）。

**本版交付**

1. 一个命令行程序：可指定题量、运算符范围、运算符个数、括号策略等参数，输出排版整齐的题面。
2. 一个自包含的单文件网页：同样的参数做成可交互控件，边调边看，可一键把排版好的题面复制走，
   也可在页面上开合答案。双击即可用，不依赖 Python、不依赖网络。
3. 一个纯逻辑核心层：不依赖命令行、不做 IO、随机源可注入；上面两个入口共用它——出题逻辑只有一份。

**本版不做**（明确排除，避免范围蔓延）

- 题库持久化、历次出题去重、用户系统
- 打印排版（页面面向屏幕；浏览器自带的打印能用，但不为纸张做版式优化）

## 2. 需求的形式化

记一道题为一个算式 `E`，运算符个数 `k ∈ {1, 2}`，运算符取自 `{+, -, ×, ÷}`。

必须同时满足的**硬约束**：

| 编号 | 约束 |
|---|---|
| H1 | 运算符个数 `k ∈ {1,2}`；每个运算符都是合法的二元四则运算 |
| H2 | `E` 中出现的**每一个数值**（叶子操作数、每一步中间结果、最终结果）都是整数且落在 `[0, 100]` |
| H3 | 任何中间结果与最终结果 `≥ 0`（不出现负数） |
| H4 | 除法：除数 `≠ 0`，且必须整除（不引入余数或小数） |
| H5 | 括号成对、嵌套不歧义 |
| H6 | 渲染时**默认**不输出等号右侧的值；答案是可选的渲染开关（§6.3） |
| H7 | （已确认）乘法限制在九九表内：**乘号两侧的操作数**都落在 `[1, 9]`，无论它是叶子还是中间结果 |

**两条推论**（由 H2 + H4 自动得出，不需要额外规则）：

- 商必定 `≤ 100`：因被除数 `≤ 100` 且被除数 = 除数 × 商，商不可能超过被除数。
- 乘法的两个因数必定 `≤ 100`：因积 `≤ 100`。

**H7 的边界说明**：九九表本身是 `1×1 … 9×9`，不含 0。用户要求"0 允许参与"与"乘法限制在九九表内"两条同时成立时，二者的交集是：**0 在加、减、除以及所有结果位置上完全放开，但不作为乘法的操作数**。若希望 `0 × n` 也出现，把 `--mul-min` 设为 0 即可（一行参数）。

## 3. 关键设计点

这一节是整份计划的技术核心，也是实现时最容易出错的地方。

### 3.1 「无括号」不等于「从左到右」

双运算符算式 `a ⊕ b ⊗ c` 在无括号时，按**运算符优先级**结合，而不是从左到右。

| 设计意图 | 渲染出的文本 | 文本的实际含义 | 是否一致 |
|---|---|---|---|
| `(6 + 7) × 5 = 65` | `6 + 7 × 5` | `6 + 35 = 41` | 否 |
| `45 + (7 × 6) = 87` | `45 + 7 × 6` | `45 + 42 = 87` | 是 |
| `3 × (14 + 9) = 69` | `3 × (14 + 9)` | 同上（括号必要） | 是 |

如果实现时"先随机产生一个左结合结构，再拼字符串"，第一行那种错误题会成批出现，而且很难在肉眼检查中发现。

**结论**：把「计算顺序」和「渲染形式」拆成两个独立步骤。

1. 先确定**计算顺序**（即表达式树形状）。
2. 计算设计值，校验 H2/H3/H4。
3. 再决定**渲染时哪些括号是必需的**，并做一次回读校验。

### 3.2 括号是否必需的判定规则

**唯一的正确判定依据（实现按这条写）**：把括号去掉后按标准优先级重新求值，若结果**不合法**（除零、不整除、负数、越界）或与设计值**不相等**，则括号必需；否则括号可省略。

这一条规则自动覆盖全部 16 种运算符组合，不需要记忆任何特例，也不会漏。

**优先级速判表（用于说明与测试对照，不作为实现依据）**：设 `优先级(+/-) = 1`，`优先级(×/÷) = 2`。

- 结构 `(a ⊕ b) ⊗ c`
  - `优先级(⊕) ≥ 优先级(⊗)` → **一定不必**加括号（枚举核验，0 例外）
  - `优先级(⊕) < 优先级(⊗)` → 通常必须加括号（如 `(6 + 7) × 5`）
- 结构 `a ⊕ (b ⊗ c)`
  - `优先级(⊕) < 优先级(⊗)` → **一定不必**加括号（如 `45 + 7 × 6`，枚举核验 0 例外）
  - `优先级(⊕) > 优先级(⊗)` → 通常必须加括号（如 `3 × (14 + 9)`）

注意两处「通常」——它们不是「一定」。存在括号本可省略的例外，见 3.4 的量化结论。

**同级时优先级表完全失效，必须看运算符本身。** 这是第二处易错点——"同级就不用括号"是错的。枚举结论如下：

| 同级结构 | 括号 |
|---|---|
| `a + (b + c)` | 冗余（恒可去） |
| `a + (b - c)` | 冗余（`a + b - c` 同值） |
| `a - (b + c)` | **必需**（与 `a - b + c` 完全不同） |
| `a - (b - c)` | **必需** |
| `a × (b × c)` | 冗余 |
| `a × (b ÷ c)` | 冗余（去括号后仍整除，且同值） |
| `a ÷ (b × c)` | **不一定**：乘数为 1 时冗余，否则必需 |
| `a ÷ (b ÷ c)` | **不一定**：同上 |

结论：`÷` 参与的同级结构必须逐题求值判定，规则表无法替代。这也是 3.2 开头那条"求值比对"必须作为实现依据的原因。

### 3.3 自校验（round-trip）——消除优先级错误的结构性保障

渲染完成后，用**独立的、只依据标准优先级**的求值器重新解析题面文本，断言其结果等于生成时的设计值。这样任何拼接/括号错误都会在生成阶段被立刻发现，而不是印到学生的作业本上。

这层校验同时是测试的主要把手：生成 10 万道题，只要有一道对不上就失败。

### 3.4 计划阶段已完成的量化核验

以上规则不是凭直觉写的。写这份计划时已用穷举脚本（叶值取遍 `[1, 99]`，4 × 4 运算符组合，两种结构）对全部情形逐例判定，结论：

| 核验项 | 结果 |
|---|---|
| `(a ⊕ b) ⊗ c` 中 `优先级(⊕) ≥ 优先级(⊗)` → 不必加括号 | 0 例外，结论成立 |
| `a ⊕ (b ⊗ c)` 中 `优先级(⊕) < 优先级(⊗)` → 不必加括号 | 0 例外，结论成立 |
| `a ⊕ (b ⊗ c)` 中 `优先级(⊕) > 优先级(⊗)`（`×`/`÷` 包 `+`/`-`） | 需括号，但**存在例外**：如 `1 × (b + c)` 可去括号 |
| 同级 `a - (b + c)` | 其中 122500 例去括号后仍合法，且**全部**需括号（0 例外） |
| 同级 `a - (b - c)` | 其中 82075 例去括号后仍合法，且**全部**需括号（0 例外） |
| 同级 `a ÷ (b × c)` | 需括号 446 例 / 不需 473 例 —— **必须逐题判定** |
| 同级 `a ÷ (b ÷ c)` | 需括号 140 例 / 不需 473 例 —— **必须逐题判定** |
| 中间值 `v ∈ [0, 100]` 是否存在可用外层运算符 | 无一例死路 |

**例外的来源已经查明**：所有"括号本可省略"的例外，充要条件都是某个操作数等于 1（例如 `(a + b) × 1` 恒等于 `a + b × 1`，故括号冗余）。

这带来一个有用的推论：**默认开启的平凡题过滤（`--exclude-trivial`，过滤 `× 1`、`÷ 1` 一类）会顺带消除全部例外**。因此在默认参数下，判定结果与上面那张优先级速判表完全一致；只有在关闭过滤时才需要依赖逐题求值判定。

**例外与叶值范围无关**：上面这份穷举是在叶值 `[1, 99]` 上做的。当前默认也采用正数叶值；即便把 `0` 作为操作数启用，它只改变某些算式的取值，不改变运算符的结合顺序。实现层面不依赖穷举结果，而是逐题现场求值判定（见下一段）。

因此最终实现取向是：**渲染一律用逐题求值判定**（简单且绝不出错），**优先级速判表退居测试断言**（用于验证求值判定在非巧合情形下与理论一致）。

## 4. 生成算法

### 4.1 基础思路：把一切归约为「两数运算」

关键观察：只要有一个函数能生成满足全部约束的 `x ⊕ y`，那么双运算符算式不过是**调用两次**——先生成内层两数运算得到中间值 `v`，再把 `v` 当作一个操作数参与外层运算。

因为中间值 `v` 天然落在 `[0, 100]`，外层运算的约束与内层完全一致，无需为双运算符单独设计规则。

### 4.2 两数合法对：四种运算的构造方式

不做"随机试、不合法就重试"的拒绝采样（在紧约束下效率低且分布偏斜），而是**按运算符直接构造**合法区间。

记号：叶子下界 `L = --min-value`（默认 1）、叶子上界 `M = --max-value`（默认 99）、结果上界 `R = --max-result`（默认 100）、乘法因子区间 `[mul_min, mul_max]`（默认 `[1, 9]`，即九九表）。

| 运算符 | 构造方式 | 结果范围 |
|---|---|---|
| `+` | 先取 `x ∈ [L, min(M, R − L)]`，再取 `y ∈ [L, min(M, R − x)]` | `[2L, R]` |
| `-` | 先取 `x ∈ [L, M]`，再取 `y ∈ [L, min(M, x)]` | `[0, M − L]` |
| `×` | 先取 `x ∈ [mul_min, min(mul_max, M)]`，再取 `y ∈ [mul_min, min(mul_max, ⌊R / x⌋)]` | `[mul_min², R]` |
| `÷` | 先取除数 `d ∈ [max(1, L), M]`，再取商 `q ∈ [q_lo, ⌊M / d⌋]`，令被除数 `x = d × q` | 商 `[q_lo, M]` |

除法用"先定除数与商、再乘出被除数"的构造顺序，可以**保证整除且被除数 ≤ M**，避免事后校验与重试。

两处边界需要说明：

- 商的取值上界写作 `⌊M / d⌋` 而不是 `⌊R / d⌋`：因为被除数 `x = d × q` 本身也是**叶子操作数**，它必须 ≤ 叶子上界 `M`（默认 99），而 `M < R`，所以 `⌊M / d⌋` 才是真正起约束作用的那个（例如 `d = 50` 时，`100 / 50 = 2` 但 `99 / 50 = 1`，取 2 会得到被除数 100 这个越界的叶子值）。
- 商的下界 `q_lo`：`L = 0` 时取 0（`0 ÷ d = 0` 合法，且让 0 可以参与除法）；`L > 0` 时取 `⌈L / d⌉`。

### 4.3 双运算符：先定结构，再定操作数

两种结构各有"已知一侧"的情形，因此需要一个**带已知操作数**的生成器：

- **结构 A（先算左）** `(a ⊕ b) ⊗ c`：先按 4.2 生成 `a, b` 得 `v1`；再以 `v1` 为**左操作数**为 `⊗` 挑 `c`。
- **结构 B（先算右）** `a ⊕ (b ⊗ c)`：先按 4.2 生成 `b, c` 得 `v2`；再以 `v2` 为**右操作数**为 `⊕` 挑 `a`。

**给定左操作数 `x`（已知值，可能是中间结果，取值范围 `[0, R]`）**，合法右操作数 `y` 的候选集（`y` 是叶子，须落在 `[L, M]`）：

| 运算符 | 候选 `y` | 无解情形 |
|---|---|---|
| `+` | `[L, min(M, R − x)]` | `x > R − L`（任何叶子都会超过 `R`） |
| `-` | `[L, min(M, x)]` | `x < L`（减去任何数都会为负） |
| `×` | `x ∉ [mul_min, mul_max]` 时无解；否则 `[mul_min, min(mul_max, ⌊R / x⌋)]` | `x` 不在九九表区间内 |
| `÷` | `x = 0` 时 `[max(1,L), M]`；否则 `[max(1,L), M]` 中 `x` 的正约数 | 无 |

**给定右操作数 `y`（已知值，可能是中间结果，取值范围 `[0, R]`）**，合法左操作数 `a` 的候选集（`a` 是叶子，须落在 `[L, M]`）：

| 运算符 | 候选 `a` | 无解情形 |
|---|---|---|
| `+` | `[L, min(M, R − y)]` | `y > R − L` |
| `-` | `[max(L, y), M]`（保证不为负） | `y > M` |
| `×` | `y ∉ [mul_min, mul_max]` 时无解；否则 `[mul_min, min(mul_max, ⌊R / y⌋)]` | `y` 不在九九表区间内 |
| `÷` | `y = 0` 时**无解**（除数不能为 0）；否则 `y × q`，`q ∈ [q_lo, ⌊M / y⌋]` | `y = 0` |

两张表的 `0` 边界必须显式特判，否则会踩两个坑：

- 乘法行按 `⌊R / y⌋` 求上界时，`y = 0` 会触发**整数除零错误**。本版把九九表约束写成**双向闭合**的（区间 `[mul_min, mul_max]` 同时卡上下界），所以 `y = 0` 在默认参数下直接被判为无解——这也正是"0 不作为乘法操作数"这条约束的落点。若把 `--mul-min` 设为 0，则 `0 × n` 合法，需要走"任意叶子均可"的分支。
- 除法行里 `y` 是**除数**，`y = 0` 时该运算符整体不可行（不是候选集为空，而是这个运算符要排除掉）。

**两张表必须互为对称**：`y` 在 `right_candidates(op, x)` 中，等价于 `x` 在 `left_candidates(op, y)` 中。这条对称性是测试的断言之一——只卡一侧的边界（例如九九表只卡上界）会立刻被它抓住：那样 `0 × 1` 会在一张表里合法、在另一张表里非法。

**避免死路**：外层运算符不是先随机再检查，而是先算出「哪些运算符在给定操作数下有非空候选集」，只在这些运算符里抽。这样生成过程不存在失败重试，也就不会出现"卡住"或"尝试次数耗尽"。

**伪代码**

```text
def gen_expression(k, cfg):
    rng = cfg.rng                      # 可注入的随机源，保证 --seed 可复现

    if k == 1:
        op = rng.choice(all_ops)
        x, y = gen_pair(op, cfg)
        return build(op, x, y)

    shape = rng.choice([SHAPE_A, SHAPE_B])        # 结构 A / 结构 B

    if shape == SHAPE_A:                          # (a ⊕ b) ⊗ c
        op1 = rng.choice(all_ops)
        a, b = gen_pair(op1, cfg)
        v1 = eval(op1, a, b)
        op2 = rng.choice(feasible_ops_given_left(v1, cfg))   # 只挑有解的运算符
        c = rng.choice(candidates_right(op2, v1, cfg))
        return build(op2, build(op1, a, b), c)

    else:                                         # a ⊕ (b ⊗ c)
        op2 = rng.choice(all_ops)
        b, c = gen_pair(op2, cfg)
        v2 = eval(op2, b, c)
        op1 = rng.choice(feasible_ops_given_right(v2, cfg))
        a = rng.choice(candidates_left(op1, v2, cfg))
        return build(op1, a, build(op2, b, c))
```

### 4.4 括号策略

「是否含括号」不是独立开关，而是由结构 + 3.2 的判定规则自动决定：

| 模式 | 含义 |
|---|---|
| `none` | 只出无括号题。实现上不是"生成后重试"，而是从**源头**只挑"在任何取值下都无需括号"的结构（§3.2 速判表），因此不需要靠重试去撞 |
| `necessary`（默认） | 括号只出现在必需处，即括号一定改变了运算顺序——每处括号都有教学意义 |
| `always` | 只出含（必要）括号的双运算符题，用于专项练习 |

三种模式都走同一条判定链：先按最保守的方式（每个内部节点都加括号）渲染，再逐个尝试去掉括号，只有在"值不变 **且** 展开过程全程不越界"时才确认去掉。

### 4.5 题量分配：配比必须精确（实现时发现并修正的缺陷）

**这是实现阶段暴露出来的一个真实缺陷，值得单列一节。**

最初的写法是"逐题随机抽运算符个数，一旦撞上去重就重新抽个数"。看起来没问题，`--ratio 1,1` 时也确实在做 50/50 的抽取。但两个因素叠加后它失效了：

- **单运算符题的题面空间远小于双运算符题**：默认参数下前者约 1.06 万种（加减各约 5000、除 472、乘 64），后者 20 万种以上。
- **撞去重的代价被另一类承担**：某一类的题面先被抽干后，它被拒绝，循环重新抽类型——于是它的缺口由另一类补上。

实测漂移（`--ratio 1,1`）：

| 题量 | 单运算符 | 双运算符 |
|---|---|---|
| 100 | 52% | 48% |
| 2000 | 46% | 54% |
| 10000 | 34.6% | 65.4% |
| 50000 | 18.9% | 81.1% |

配比是用户的显式设定，不能被这种副作用悄悄改掉。**修正后的做法**：

1. **先把题量按 `ratio` 精确分配到各类**（最大余数法：先取整，余数按小数部分从大到小补齐，保证总和恒等于 `count`）；
2. 每一类各自去凑自己的名额，类内独立去重，互不干扰；
3. 各类分段生成后整体混排，避免卷面前半页全是同一类型。

修正后 6000 题的实测结果是精确的 3000 / 3000。

**题面空间耗尽时怎么办**——三类题的空间都是有限的，物理上不可能无限出：

- 默认（`allow_repeat = False`）：停止该类，**如实报告缺口**（"1 个运算符的题需要 50000 道，不重复的题面只够 10625 道"），并给出放宽建议。绝不静默少给，也绝不静默改变配比。
- 开启 `--allow-repeat`：允许重复使用已出过的题面，先把题量凑满，并在报告里说明重复了多少道。

判定"空间耗尽"用的是"连续多次抽到已出现过的题面"。这个判据只能在"几乎抽干"和"完全抽干"之间取平衡：空间剩得越少，连续撞车越容易发生，两者行为上难以区分。阈值取 1000——空间够用时它不可能被触发，空间用尽后也只多花不到 0.1 秒。实测它能在单运算符题的 1.06 万种空间里取出 10625 道（99% 以上），不会明显过早收手。

### 4.6 去重与可复现

- 以**规范化题面文本**作为去重键（去空格、统一运算符符号），保证同一份卷子内不重复。
- 每行排几题由 `--per-line` 控制，排版按显示宽度对齐（全角字符算 2 列）。
- 随机源由外部注入（`random.Random(seed)`），不依赖全局随机状态。给定 `--seed` 即得到完全相同的题目集合——便于出题留档、也便于测试与问题复现。

## 5. 数据结构

```text
Node            表达式树节点（叶子与内部节点同一个类型）
  ├─ value     : 该子树的计算结果（生成时即算出，后续校验/渲染/判重直接复用）
  ├─ op        : 运算符；叶子为 None
  ├─ left      : Node | None（叶子为 None）
  ├─ right     : Node | None
  ├─ is_leaf()          : op is None
  ├─ iter_nodes()       : 先序遍历自身与全部后代
  ├─ iter_operators()   : 只要内部节点
  ├─ leaves()           : 全部叶子值
  ├─ operator_count()   : 运算符个数
  ├─ depth()            : 树深
  └─ to_dict()          : 序列化

Problem         一道题
  ├─ root      : Node
  ├─ text      : 题面文本（渲染后、含必要括号、不含答案）
  ├─ answer    : 设计值 —— 始终持有；渲不渲染由开关决定
  ├─ text_norm : 去重用的规范化文本
  ├─ operator_count : 属性，转发给 root
  └─ to_dict() : 序列化，供后续接口层直接返回 JSON
```

设计要点：

- `Problem` 同时持有题面与答案，**是否显示答案由渲染层决定**。"默认不给结果"因此只是一行渲染逻辑——
  后来加答案开关时，生成逻辑一行都没动（§6.3），这条设计得到了验证。
- **节点上没有"是否需要括号"这个字段**。括号是渲染时刻的决策：渲染层按 §4.4 的判定链现场求值比对得出，而不是在构造树时预先算好。这样括号判定永远只有一处逻辑，不会出现"树上的标记"与"实际渲染"两套真相。
- 树结构里**不区分结构 A / 结构 B 的类型标记**——结构由 `left`/`right` 是否叶子自然表达，序列化后前端也能直接看出结构。

## 6. 项目结构与前端

```text
SimpleCalculate/
├─ 计划书.md                        # 本文件
├─ README.md                        # 使用说明（安装、命令示例、参数速查、网页版）
├─ 口算练习.html                     # 网页版：自包含单文件（样式/引擎/界面脚本/图标全内联）
├─ pyproject.toml                   # 包与依赖声明、命令行入口注册
├─ src/
│  └─ simple_calculate/
│     ├─ __init__.py                # 对外导出的公共接口
│     ├─ __main__.py                # 支持 python -m simple_calculate
│     ├─ config.py                  # 生成参数（dataclass）：范围、运算符、数量、种子…（最底层，不依赖其他模块）
│     ├─ model.py                   # Node / Problem 数据结构与序列化
│     ├─ core.py                    # 两数合法对构造（4.2 / 4.3）
│     ├─ generator.py               # 题量分配、单/双运算符算式生成、去重（4.3–4.5）
│     ├─ validate.py                # 硬约束判定 + 独立优先级求值器 + round-trip 校验
│     ├─ render.py                  # 括号决策 + 文本渲染，题面/答案分离，排版对齐
│     └─ cli.py                     # 命令行入口（参数解析 → 调用 → 输出）
├─ tests/
│  ├─ test_core.py                  # 两张候选表的对称性、边界、与暴力枚举对齐
│  ├─ test_generator.py             # 批量采样、各模式行为、题量配比
│  ├─ test_validate.py              # 优先级求值器与 round-trip
│  ├─ test_page.py                  # 单文件页面：自包含性、内联标记、答案开关默认态
│  └─ test_engine_parity.py         # 页面内联引擎 × Python 校验器的交叉验证（见 6.2）
```

**依赖方向是单向的**（这是刻意的，用于保证校验器的独立性）：

```text
config  ←  model  ←  core  ←  generator  ←  cli
                  ↖  validate  ↖  render
```

`cli` 是唯一的 Python 入口，只往生成器上调。

`validate` 只依赖 `config` 和 `model`，**不依赖 `core`/`generator`**。所以"独立求值器"是真的独立：生成逻辑写错，校验逻辑不会跟着一起错。同理，`render` 依赖 `validate` 的求值器来做括号决策，而不是复用 `core.apply_op`。

**为前端预留的三处接口（网页版正是靠它们接上来的，未再改动生成逻辑）**

1. **core 层是纯函数**：无 IO、无全局状态、随机源注入 → 接口层直接调用即可。
2. **`Problem.to_dict()`**：生成结果可直接序列化为 JSON，前端无需理解表达式树结构。
3. **`render.py` 是插件式渲染层**：文本渲染器直接复用来产出"复制题面"的纯文本，也用来决定答案开关关掉时卷面长什么样。

命名统一用 ASCII；文件内容为 UTF-8。

### 6.1 网页版为什么是一个自包含单文件

结论先说：**这张页面不联网、不起服务，双击就可用**。这不是图省事，而是三条浏览器硬约束逼出来的唯一可行解。

`file://` 下实测的三条约束：

| 能力 | 结果 |
|---|---|
| 同目录的经典 `<script src>` | ✅ 能加载 |
| ES module（`<script type="module">`） | ❌ 被 CORS 拦下 |
| `fetch()` 抓本地服务 | ❌ 必失败（页面的 Origin 是 `null`） |

也就是说，双击打开时页面**拿不到任何外部资源**——出题能力只能跟着页面走进浏览器。于是把样式、引擎、界面脚本、图标全部内联进一个 `口算练习.html`：它是唯一的交付物，拷给别人只需给这一个文件。

**中途试过并否掉的路：起一个本地 HTTP 服务当后端。** 最早实现里确实有一个 `web.py`（标准库 `http.server`），但它存在的理由只有一个：绕过上面第三条约束。等出题引擎进了浏览器，它就没有任何优势了——两条路径被交叉验证锁成等价（18 组参数、2000 余道题硬约束零违反、卷面排版逐字符一致），而内置引擎快两个数量级（20 题 4 ms，Python 出两万题要 6 秒）。于是服务连同它的接口一起删掉：少一条链路、少一类测试、少一处文档要维护。

**代价与处理**：出题逻辑因此有了两份实现。这不能靠"照着抄了一遍"的自觉，靠的是 §6.2 的三层保障。

**保留的部分**：`cli.py` 与整个 Python 包都留着，而且不能删——它现在有两个身份：一是命令行工具，二是**交叉验证的裁判**（§6.2）。后者比"后端"这个身份值钱得多。

顺带一提：命令行与网页版的**默认值只有一个来源**。页面启动时向引擎要 `meta()`，而引擎的默认值逐字段对应 `Config`，并有测试锁住两者一致（§9）——不存在"JS 里再抄一份默认值"这种漂移点。

### 6.2 页面内联的引擎：多一份实现，怎么让它不漂移

既然"双击就能用"要求生成逻辑进入浏览器（6.1 的三条硬约束），那就必须正面处理"两份实现"这件事——本项目在 §4.5 已经领教过一次"两边悄悄对不上"的代价。

**先试过、并且否掉的路：预生成题库。**

思路是让 Python 把题目全部算好存成数据文件，页面只做筛选——这样数值合法性仍由唯一实现保证，浏览器不碰数值构造。实测之后放弃了：

| 方案 | 实测代价 |
|---|---|
| 预生成题库 + 页面本地筛选 | 默认配置下全量题面 **204.8 万条 / 18.2 MB**；九九表完全放开则 236.8 万条 / 20.9 MB。对一个"双击打开的小工具"太重，而且只覆盖生成时选定的那一档参数 |
| 浏览器版引擎（本版选择） | 零数据文件；代价是生成逻辑多一份实现，用下面的三层保障兜住 |

（那个 204 万是实测出来的，不是估的——我原本以为双运算符题只有二十几万种，实际每个内层结果后面都能接上百来种外层写法。）

**页面里那段内联引擎（`id="sc-engine"`）与 Python 版逐函数对应**：每一节都标注了它对应 `config.py` / `core.py` / `model.py` / `render.py` / `validate.py` 的哪个部分，移植时不"顺手优化"，连遍历顺序与抽样顺序都保持一致。

但"我照着抄了一遍"不算保证。真正的保证是三层：

1. **逐题自校验**：引擎每出一题就用自带的独立求值器复算题面，不通过即抛错——与命令行版行为一致：宁可失败，不输出错题。
2. **交叉验证**：`tests/test_engine_parity.py` 按 `id="sc-engine"` 把引擎从页面里抠出来，用 Node 驱动它在 18 组参数下成批出题（2000 余道），把每道题的题面与表达式树导回 Python，交给项目原有的 `validate.validate_problem` 逐题复核。该校验器本就不依赖生成器（§6 的依赖方向图），所以这是一次真正独立的复核，而不是让同一份逻辑自证。
3. **锁住易漂移的细节**：同一套测试还比对配置默认值、纯文本卷面的排版（与 `render_sheet` 逐字符一致）、单双运算符配比的精确性。

这条链在开发中确实抓到了一个缺陷：移植参数收敛时把 `ops` 当成数字数组转换，`['+','-']` 变成了 `[NaN, NaN]`——交叉验证第一次运行就报了出来。这种事靠肉眼 review 是看不出来的。

**顺带解决掉的一处不一致**：此前页面与服务端各有随机源，同一个种子在两边给出的题目不同。服务下线后只剩一个随机源，**同一个种子在任何地方都给出同一份题**（引擎内部同种子必然一致，且默认值与 Python 侧逐字段对齐）。

### 6.3 答案开关

答案一直算好并留在 `Problem` 里（见 §5 的数据结构）。本版把它做成一个**视图开关**：

| 入口 | 开关 | 默认 |
|---|---|---|
| 网页版 | 顶栏「显示答案」 | 关 |
| 命令行 | `--show-answer` | 关 |

两条实现上的约束：

1. **切开关不许换题。** 页面在生成时就把答案一起取回存在内存里，开关只重画卷面。若等开关打开再去要一次数据，题目就会换一批——"我想看一眼答案"不该有这种副作用。
2. **排版只有一份实现。** "复制题面"的纯文本由引擎的 `renderSheet` 现场排（与 Python 的 `render_sheet` 逐字符一致，有交叉验证盯着），而不是从 DOM 里抠文本——抠出来的会丢掉列对齐，那就白排了。

顺带一个屏幕版的排版约束：**算式绝不折行，答案也不折**。"每行排几题"因此是**上限**而非硬指标——窗口不够宽时列数自动少一档，而不是把字压小或让答案掉到下一行；面板上会写明实际排了几列。列数由窗口宽度、左侧面板、纸的页边距三者共同决定，算不出来，只能量（`getComputedStyle` 读实际轨道数）。

## 7. 参数与输出

### 7.1 命令行参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-n, --count` | 20 | 题目数量 |
| `--ops` | `+-*/` | 参与随机抽取的运算符集合，如 `--ops +-` 或 `--ops 加减` |
| `--weights` | 均等 | 各运算符权重，如 `+=3,-=3,*=2,/=2`（低年级可提高加减权重）；缺省的运算符按 1 计 |
| `--operators` | `1,2` | 每题的运算符个数，`1` / `2` / `1,2` 混合 |
| `--ratio` | `1,1` | 与 `--operators` 对应的题量配比，如 `--operators 1,2 --ratio 3,7` |
| `--min-value` | 1 | 叶子操作数下界；要让 0 参与运算，设为 0 并加 `--no-exclude-zero-forms` |
| `--max-value` | 99 | 叶子操作数上界 |
| `--max-result` | 100 | 中间结果与最终结果的硬上界 |
| `--mul-min` | 1 | 乘法因数下界。设为 0 可让 `0 × n` 出现（默认按九九表不含 0） |
| `--mul-max` | 9 | 乘法因数上界。默认 9 即乘法限制在九九表内 |
| `--paren` | `necessary` | `none` / `necessary` / `always`（见 §4.4） |
| `--no-zero-result` | 关闭 | 加上即禁止结果为 0（注意 `0 + 7` 的结果不是 0，不受影响） |
| `--exclude-trivial` | 开启 | 过滤 `n × 1`、`1 × n`、`n ÷ 1`、`0 ⊕ 0` 这类无训练价值的题；用 `--no-exclude-trivial` 关闭 |
| `--exclude-zero-forms` | 开启 | 让 0 只能作为最终结果出现，不参与任何运算；用 `--no-exclude-zero-forms` 关闭 |
| `--allow-repeat` | 关闭 | 不重复的题面不够时，允许重复使用已出过的题面把题量凑满（见 §4.5） |
| `--per-line` | 4 | 每行排几道题 |
| `--seed` | 随机 | 固定随机种子，结果可复现 |
| `--out` | 控制台 | 输出到文件（`.txt` / `.md`），后续可扩展 `.csv` |
| `--no-blank-line` | 关闭 | 加上即行与行之间不留空行 |
| `--show-answer` | 关闭 | 加上即连答案一起输出（答案写在题干等号右侧） |

内部运算符表示统一用 ASCII（`+ - * /`），渲染层负责映射为排版用的 `+ − × ÷`。这样命令行参数、去重键、序列化 JSON 全部是 ASCII，避免编码与比对歧义。

### 7.2 输出样式（题面，每行 4 题）

下面是 `-n 20 --seed 42` 的**实际输出**（非手绘示例）：

```text
  1. 75 + 13 =             2. 87 ÷ 29 =             3. 27 − 24 =             4. 6 × 4 ÷ 2 =

  5. 65 + 0 ÷ 47 =         6. 29 − 16 =             7. 71 + 6 =              8. (14 + 19) ÷ 3 =

  9. 90 − 4 × 8 =         10. 4 × 4 =              11. 48 + 6 − 54 =        12. 3 + 94 =

 13. 27 + 7 × 5 =         14. 3 + 11 =             15. 44 ÷ 44 =            16. 87 − 41 + 14 =

 17. (31 − 16) ÷ 15 =     18. 98 − 37 + 14 =       19. 94 − 13 =            20. 59 + (68 − 31) =
```

可以看到几个约束都在生效：

- 第 4 题 `6 × 4 ÷ 2` 是无括号双运算符题，按标准优先级是 `(6×4)÷2 = 12`——与设计值一致（不存在 3.1 那个"先左结合再拼字符串"的陷阱）。
- 第 8、17、20 题带括号且括号必需：去掉括号后要么语义改变、要么展开过程越界。
- 第 5 题 `65 + 0 ÷ 47`：0 作为被除数参与运算，合法（`0 ÷ 47 = 0`，除数非零）。
- 第 11 题结果为 0（`48 + 6 − 54`）——已确认允许。
- 所有中间值与结果都在 `[0, 100]` 内，乘法两侧操作数都在九九表内。

## 9. 验证方案与实测结果

因为约束是"全称命题"（**每一个**数值都要合法），验证方式必须是批量采样而非抽查。

**测试套件**：65 项，`python -m unittest discover -s tests -t tests`。

| 核验项 | 做法 | 实测结果 |
|---|---|---|
| 批量断言（H1–H7） | 请求 10 万题，逐题断言全部叶子值、中间值、最终值均为 `[0,100]` 内整数；无负数；除数非零且整除；乘法两侧操作数都在九九表内；括号配对 | ✅ 零违反（实得 60625 题，缺额原因见下） |
| 回读校验 | 用独立求值器解析题面文本，结果必须等于 `answer`（§3.3 的 round-trip） | ✅ 60625 题全部一致 |
| 两表对称性 | `y ∈ right_candidates(op, x)` 必须等价于 `x ∈ left_candidates(op, y)`，遍历 7 组配置 × 4 运算符 × 全定义域 | ✅ 0 处不一致 |
| 候选集合法性 | 两张表给出的候选永远是合法叶子（在 `[L, M]` 内、乘法在九九表内） | ✅ 0 处越界 |
| 与枚举对齐 | `can_gen_pair` 的判定与实际 `gen_pair` 行为逐一对齐 | ✅ 一致 |

**分布检查（1000 题规模，实际使用量级）**：

| 指标 | 实测 |
|---|---|
| 单 / 双运算符 | 精确 50% / 50% |
| 四个运算符出现占比 | 加 34%、减 33%、乘 11%、除 22% |
| 含括号的双运算符题 | 约 30% |
| 答案均值 | 约 38（最大 100） |
| 唯一题面 | 1000 / 1000（无重复） |

两点需要说明（**不是缺陷，是约束的必然结果，但值得知道**）：

- **乘法的出现占比明显低于加减**（约 11% vs 各 33%）。原因是九九表约束让乘法的题面空间只有 64 种（`[1,9]×[1,9]` 去掉 `×1` 后），而加减各有约 5000 种；双运算符题里外层能否放乘号，还要看中间结果是否落在 `[1,9]` 内，进一步收窄。需要更多乘法题时，用 `--weights *=4` 一类参数提高其权重，或把 `--mul-max` 放宽。
- **答案偏小值**（10 以内约占三成）。这是减法与除法的构造方式带来的：`a − b` 中 `b` 在 `[0, a]` 内均匀取值，结果自然偏向小值；除法的商也偏小。若需要更均匀的答案分布，需要引入分层抽样，属于 M5 的可选改进。

## 10. 已确认的取舍

以下几条取决于教学取向、不属于技术事实，已按你的决定固化进默认参数：

| # | 问题 | 已确认的决定 | 落点 |
|---|---|---|---|
| 1 | `0` 是否作为操作数 | **默认不允许；最终答案仍可为 0** | 默认 `--min-value 1`；练习 0 时同时设 `--min-value 0 --no-exclude-zero-forms` |
| 2 | 是否限制乘法在九九表内 | **限制** | `--mul-min 1 --mul-max 9`（默认） |
| 3 | 结果是否允许为 `0` | **允许** | `allow_zero_result = True`（默认）；要禁止就加 `--no-zero-result` |
| 4 | 括号默认怎么出 | 括号只出现在必需处 | `--paren necessary`（默认） |
| 5 | 是否过滤 `n × 1` / `n ÷ 1` | 默认过滤 | `--exclude-trivial`（默认开启） |
| 6 | 运算符个数默认配比 | 两者均等，且配比精确兑现 | `--operators 1,2 --ratio 1,1`（默认） |
| 7 | 每行排几题 | 默认 4（网页版为上限，见 §6.3） | `--per-line 4`（默认） |

默认情况下，0 不作为操作数，也不作为双步算式的中间结果；它仍可作为最终答案（如 `8 − 8 = 0`）。命令行练习 0 参与运算时，同时设置 `--min-value 0 --no-exclude-zero-forms`。乘法仍默认限制在九九表的 `1×1 … 9×9`，需显式设置 `--mul-min 0` 才会出现 `0 × n`。网页端的“允许 0 参与运算”开关会自动应用这两项设置。
