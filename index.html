CodeLine · 代码行统计工具

2026.09 · C++11 / 原生 JavaScript

提供 C++ 命令行版和浏览器版，统计 C / C++ / Java / Python 源文件。浏览器版可选择本机文件夹，文件只在本地处理。

  • 在 MinGW 头文件目录统计 411 个文件、134,350 行代码，耗时 2.7 秒。
  • 定位并修复整盘扫描因 Windows 长路径拼接失败而静默跳过目录的问题。
  • 用独立 Python 实现交叉验证，13 万行统计差异为 9 行（0.007%）。
查看实现决策与验证细节
背景
课程要求实现一个代码行统计器。本机 MinGW 是 GCC 6.3，没有 std::filesystem，目录遍历只能自己用平台 API 写；作业又要求「能扫整盘」。这两条一起把难度压在了路径与 IO 上，而不是统计规则上。
我的决策
不用 std::filesystem，改成 Win32 FindFirstFileA 与 POSIX opendir 双分支，显式栈迭代递归，避免深目录爆栈。逐行扫描走字符状态机，用 inBlock / inLine 两个状态记录位置，一旦进入字符串字面量就整体跳过——这样 "http://x" 里的 // 不会被当成注释。读文件用 std::getline 流式处理，不整个载入内存。
结果
在 D:/MinGW/include 上实测 411 个文件、134350 行代码，耗时 2.7 秒；整盘扫描 C:\ 得到 6957 个文件、600893 行代码，冷启动 56 秒、二次 13–16 秒。
真正值钱的是查出的那个隐蔽 bug：整盘扫描返回全 0、只用了 0.168 秒，但扫任何子目录都正常。根因是 \\?\ 长路径前缀会关闭系统路径规范化，而驱动器根目录经 GetFullPathNameA 后保留结尾反斜杠，于是拼出 \\?\C:\\Windows 这种双反斜杠，直接报 ERROR_INVALID_NAME(123)，整棵子树被静默跳过。抽出统一的 joinPath() 修掉后恢复正常。
统计口径另用 Python 的 tokenize 写了独立实现交叉验证：相同批次下 13 万行只差 9 行（0.007%），判定实现正确。

SimpleCalculate · 小学口算出题器

2026.09 · Python 3.13 + 原生 JS

面向小学生的四则运算题目生成器，命令行与网页两种用法。题目不重复、可复现，并且保证所有数值（含每一步中间结果）都落在 [0, 100] 内、除法除得尽、乘法不超出九九表。

  • 用独立校验器复核 27,950 道题，硬约束违反 0，排版不一致 0。
  • 修复去重导致的题型比例漂移，并解决 --mul-min 0 路径崩溃。
  • 网页端布局覆盖 68 组窗口与设置组合，未出现折行。
查看实现决策与验证细节
背景
核心约束是「所有数值永不越界」——这是一条全称命题，靠抽样测不出来。最容易走歪的路是用 JS 把生成逻辑重写一遍给网页用，那等于把唯一真相源变成两份实现，成批出题时的漂移极难察觉。
我的决策
生成改为「按运算符直接构造合法区间」，再配一个不依赖生成器的独立求值校验器做回读复核。浏览器版把引擎内联进页面（file:// 下 fetch 必失败、ES module 被 CORS 拦，只能走经典脚本），同时用 Node 驱动引擎成批出题、回炉交给 Python 校验器逐题复核，防止两份实现漂移。括号只在渲染层现场求值决定要不要加，树上不存这个字段，避免两套真相。
结果
77 项测试、交叉验证 27950 道题，硬约束违反 0、排版不一致 0。
页面上线后做分布检查，发现单 / 双运算符配比随题量漂移：100 题时 52:48，5 万题时变成 18.9:81.1。根因是「逐题抽类型 + 全局去重 + 撞重复就重抽」——单运算符题只有约 1.06 万种题面，抽干后被拒绝的代价全由空间大得多的双运算符题补上。改成最大余数法先精确分配名额、再各类独立去重，6000 题实测精确到 3000:3000。
顺带暴露一个真崩溃：--mul-min 0 这条路径在候选集构造时对操作数 0 做整除，直接 ZeroDivisionError，之前完全没有测试覆盖。
网页版为自包含单文件，20 题出题耗时 4 毫秒（Python 版两万题约 6 秒）；用无头 Edge 跑了 68 组「窗口宽度 × 每行题数 × 答案开关」的布局矩阵，折行 0 组。
